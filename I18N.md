# UI localization

UI language follows Obsidian at plugin load: Korean language codes use `ko`; all other languages use `en`. Reload the plugin after changing Obsidian's language. There is no separate plugin language setting or React context.

`src/i18n/en.ts` defines the translation keys and parameter types. `ko.ts` must implement the same dictionary. TypeScript checks missing keys and parameter types. This project uses TypeScript 4.7, so dictionaries use type annotations rather than `satisfies`.

React components, settings, commands, and notices share the same API:

```ts
import { t, getFormatLocale } from "../i18n";

t("common.refresh");
t("videos.count", { count: 12 });
new Date().toLocaleString(getFormatLocale());
```

Translate whole sentences, including count-dependent text, instead of concatenating translated fragments. Add function parameters to the translation function implementation signature when introducing a new parameter shape; keep them consistent with the English dictionary.

Migrate existing `UI_TEXT` entries and their consumers together. Do not keep duplicate copies of migrated text. The settings, liked-video and playlist views, subscription view, saved-summary view, transcript reader, comments and playlist modals, shared controls, authentication, cache ownership, and release notes now use the same dictionary API. Review new UI and notices in their source modules; provider and file-system errors may still include untranslated external error details.

The legacy `src/constants/uiText.ts` module is no longer referenced by UI code. It remains as old source text and should be removed only as a separate cleanup after checking downstream consumers.

UI localization does not change transcript or AI summary language, persisted identifiers, template variables, saved notes, or existing summaries. These retain their existing settings and storage contracts.

Run `node scripts/verifyI18n.mjs` and `npm run build` to check the foundation.
